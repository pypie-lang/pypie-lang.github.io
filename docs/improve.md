# Website Architecture Review and Redesign Proposal

Status: proposal — 2026-06-10

Implementation note — 2026-06-10: sections 2.2 through 2.5 have been addressed
in the website build. Documentation pages now use `site.config.js`,
`templates/doc-page.html`, `scripts/generate-site.js`, `assets/site.css`, and
`top-actions.ts`; the old per-section templates, generators, shared render
runtimes, inline page styles, and theme URL propagation have been removed from
the active system. This document remains useful as the architectural rationale
and as a roadmap for later content-authoring work.

Implementation note — 2026-06-10 (second pass, full visual revamp): the
aesthetics program in section 4 is now implemented. The landing page is a
hero + playground + feature cards (playground stays on the main page); the
header/footer chrome, favicon, per-page canonical/OG meta, `sitemap.xml`,
`robots.txt`, and previous/next chapter pagers are generated by
`scripts/generate-site.js`; fonts are self-hosted woff2 in `assets/fonts/`;
chat bubbles no longer have a forced min-height; `playground/index.html` is a
redirect to the home page. Existing content under tutorial, manual,
installation, and updates was preserved unchanged. Still open from the
roadmap: §2.6/3.5 (stop committing artifacts; CI build + deploy) and §3.2
(Markdown + compiler-verified snippets as the authoring format).

This document analyzes the architectural problems of the PyPie website as it
existed before the 2026-06-10 documentation-system migration, then lays out a
target design with fundamental improvements to maintainability and aesthetics,
and an incremental migration plan.

---

## 1. Pre-migration architecture (summary of facts)

- Static site for GitHub Pages (`CNAME`), no framework.
- Three parallel documentation engines, one per section:
  - `learn/` — `chapter-template.html` + `generate-chapter-indexes.js` + `learn-shared.ts`
  - `manual/` — `chapter-template.html` + `generate-chapter-indexes.js` + `manual-shared.ts`
  - `updates/` — `chapter-template.html` + `generate-chapter-indexes.js` + `manual-shared.ts`
- Chapter content is authored as TypeScript: each `*/main.ts` is an IIFE that
  calls `window.PYPIE_LEARN_RENDER(...)` with dialog text in JS strings (a
  homegrown markup: `!!keyword!!`, backticks, `[label](href)`) and code
  samples as hand-written AST object literals rendered by `code-types.ts`.
- Generated `index.html` shells contain no content; everything is injected
  client-side at load time.
- Every HTML page embeds its full stylesheet inline, including its own copy of
  the font `@import` (23 copies) and its own theme palette.
- TypeScript is compiled with `tsc --module none` (global-scope IIFEs, flags in
  the Makefile, no `tsconfig.json`); only the playground uses esbuild/modules.
- Compiled `.js`, generated `.html`, `playground/dist/` (1.3 MB bundle), and
  `node_modules/typescript` + `node_modules/.bin/tsc` are committed to git.
- Theme switching is implemented three times (`top-actions.ts`,
  `learn-shared.ts`, `manual-shared.ts`) and propagated by appending a
  `?theme=` query parameter to every navigation link.
- The root `index.html` is the playground; `playground/index.html` is a
  drifted near-duplicate of it. `installation.html` is a redirect stub;
  `language-reference.html` and `technical-template.html` are orphans;
  `benchmarks` (JSON) and `draft/` (prose files with spaces in their names)
  sit in the deploy root.

## 2. Architectural problems

### 2.1 Content is authored as executable TypeScript (the core problem)

A tutorial chapter is not data; it is a program. `learn/transformer/main.ts`
is **5,968 lines** of TypeScript to express what is, in substance, a few pages
of dialog and a few dozen PyPie snippets. `learn/cnn/main.ts` is 4,081 lines,
`learn/corr/main.ts` 3,468. Consequences:

- **Hand-written ASTs.** Every code sample is an object-literal AST
  (`{kind: "FunctionDef", name: {kind: "Identifier", role: "fn", ...}}`).
  Writing `def softmax(x): ...` takes ~40 lines of nested literals. This is
  so error-prone that `AGENTS.md` exists primarily to police "sloppy AST
  patterns" — a rulebook for a problem the architecture created.
- **Types and type-hover info are transcribed by hand** (`type:
  "Tensor[float][[l, n]]"` strings inside identifiers). The PyPie compiler
  already knows these types; the website maintains a second, manually-synced
  copy that silently drifts as the language evolves. This directly violates
  the "one source of truth for PyPie analysis" invariant the project itself
  states in `docs/playground_hover.md`.
- **A homegrown half-Markdown.** `learn-shared.ts` implements inline code,
  bold/keywords (`!!…!!`), and links via regex — a partial, divergent
  reimplementation of Markdown that every author must learn.
- **Editing friction.** Fixing a typo means editing a TS string inside a
  5,000-line file, recompiling, and committing both `.ts` and `.js`.
  Reviewing a content PR means reading ASTs, not prose.

### 2.2 Three parallel copies of one documentation engine

`updates/manual-shared.ts` is a verbatim copy of `manual/manual-shared.ts`
except for the series list (~20 of 635 lines differ). The three
`generate-chapter-indexes.js` differ by two strings. The three
`chapter-template.html` files share ~90% of their 380–475 lines, already with
drift (the chat-bubble CSS exists only in learn's copy; `--section-bg` only in
manual's). Every visual or behavioral fix must be applied three times and
historically hasn't been — that is what produced the drift.

### 2.3 Static content rendered client-side

Every generated `index.html` is an empty shell (`<h1 data-learn-title></h1>`)
filled in by four sequential classic `<script>` tags. Consequences:

- **Zero SEO.** Search engines and link-preview bots see empty pages. There
  are also no `<meta name="description">`, no Open Graph tags, no sitemap, no
  favicon anywhere in the repo. A language fighting for adoption is invisible
  to search.
- **No content without JS**, and a visible flash/reflow as content and theme
  are applied after load.
- Page titles are static per-template ("PyPie - Tutorial" for all eight
  chapters), so browser history, bookmarks, and search results cannot
  distinguish chapters.

### 2.4 The stylesheet is duplicated and divergent across 23 pages

Each page inlines ~300–400 lines of CSS. There are at least **three divergent
design-token vocabularies** for the same brand:

- playground/root: `--page-bg`, `--surface`, `--accent`, plus a third theme
  (`:root` light) that exists nowhere else;
- learn/manual/updates: `--hero-bg`, `--panel-bg`, `--link-color`, with a
  dark `:root` default;
- `technical-template.html`: yet another snapshot.

The same conceptual color ("Solarized paper background") is hand-repeated in
each file. A palette tweak is a 20-file find-and-replace; in practice the
palettes have already drifted (the docs' dark `:root` vs the playground's
light `:root`, different accent hues).

### 2.5 Theme system: three implementations and URL pollution

Theme state lives simultaneously in `localStorage`, the `<body>` class, and a
`?theme=` query parameter that is rewritten into **every** nav link and into
the address bar via `history.replaceState`. Three separate scripts implement
reading/syncing it. Costs: shared URLs carry stale theme choices, canonical
URLs fork into `?theme=theme-solaris` / `?theme=theme-dark` variants (bad for
caching and SEO), and any new page must wire all of it again. All of this
replaces what one CSS attribute plus `prefers-color-scheme` does natively.

### 2.6 Generated artifacts and the toolchain are committed

`git ls-files` contains every compiled `main.js`, every generated
`index.html`, the 1.3 MB `playground/dist/main.js`, **and the TypeScript
compiler itself** (`node_modules/typescript/**`, `node_modules/.bin/tsc`,
whitelisted in `.gitignore`). Consequences: every content edit produces noisy
double-diffs (source + artifact), artifacts can drift from sources with no
check, merge conflicts in generated files, and a vendored compiler that
upgrades by committing thousands of files. Cache busting is manual, hand-typed
query strings (`main.js?v=20260610-line-examples`) that depend on a human
remembering to bump them.

### 2.7 No module system for site code

`tsc --module none` forces everything into global-scope IIFEs communicating
through `window.PYPIE_*` globals. Because nothing can be imported, the types
(`LearnDialogMessage`, `LearnPageConfig`, …) are **copy-pasted into every
chapter file** — eleven slightly different declarations of the same types —
and `tsc` cannot check that a chapter's config actually matches what
`learn-shared.ts` expects. Script load order in the template is load-bearing
and unchecked. Meanwhile the playground uses esbuild with real ESM: two build
systems, two idioms, in one small repo.

### 2.8 Information-architecture drift

- The homepage *is* the playground (title "PyPie Playground"), with the
  project's only self-description collapsed into a bottom "About" drawer.
  First-time visitors get an empty editor before they learn what PyPie is.
- `playground/index.html` still exists and has already drifted from the root
  copy (diff shows divergent layout rules) — which one is canonical?
- The "Updates" nav link is hardcoded to `updates/5_25_2026/index.html` in
  `top-actions.ts`; publishing each new update post requires editing the nav
  component. There is no updates index page and no feed.
- Orphans/stubs deployed to production: `language-reference.html` (old
  manual), `technical-template.html` (an internal template), `installation.html`
  (meta-refresh stub), `benchmarks` (raw JSON), `draft/` (working notes).
- The Makefile works around its own content with `! -path '* *'` because
  `draft/` filenames contain spaces.

### 2.9 Developer experience gaps

No `tsconfig.json` (compiler flags hide in the Makefile), no dev server, no
watch mode, no formatter or linter config, no CI: nothing builds or
link-checks PRs, so a broken build or dangling link ships silently. The
README's "add a page" recipe is four manual steps plus an edit to a shared
registry — and a fifth, undocumented step (bump the cache-buster) when
touching the playground.

## 3. Target design — maintainability

### 3.1 One documentation engine, configured three ways

Collapse `learn/`, `manual/`, `updates/` into a single generator + single
template + single runtime, driven by one site manifest:

```
site.config.ts
  sections:
    learn:   { title: "Tutorial", numbered: true,  chapters: [...] }
    manual:  { title: "Manual",   numbered: true,  chapters: [...] }
    updates: { title: "Updates",  numbered: false, dateSorted: true }
```

The manifest is also the single source for top navigation (no more hardcoded
`updates/5_25_2026` in `top-actions.ts`) and for prev/next links, the updates
index page, the sitemap, and an RSS/Atom feed for updates.

### 3.2 Content as data: Markdown in, HTML out

Author chapters as Markdown files with front matter:

```markdown
---
title: The Transformer
section: learn
order: 8
lead: Attention, typed end to end.
---

@@dialog
W: A transformer is built from !!self-attention!! blocks...
D: What does the type of `AttentionParams` look like?
@@

```pypie
class AttentionParams[n: int, d: int]:
    q: LinearParams[float, n, d]
    ...
```
```

- The dialog block is a tiny custom container on top of standard Markdown —
  keep the `!!keyword!!` convention (it feeds the keyword panel) but let a
  real Markdown parser (`markdown-it` + one container plugin) handle
  everything else. Delete the regex markup engine in `learn-shared.ts`.
- **PyPie code blocks are plain PyPie source, not ASTs.** At build time, run
  each fenced `pypie` block through the real toolchain — the same
  `pypie-lang` wheel the playground already runs in Pyodide can run in a
  build step (Node + Pyodide, or a native CLI) — and emit the highlighted
  HTML with type-hover metadata as `data-type` attributes. This restores the
  `docs/playground_hover.md` invariant (one analysis path) for the *docs*,
  not just the playground: when the language changes, chapters re-check and
  re-annotate automatically, and a snippet that no longer type-checks fails
  the build instead of silently lying to readers.
- `code-types.ts`'s renderer survives as the build-time HTML emitter; the
  hand-written AST literals, the per-chapter type transcriptions, and the
  AST style guide in `AGENTS.md` all become unnecessary.
- Expected effect on volume: the ~26,000 lines of chapter TS collapse to a
  few thousand lines of readable Markdown + PyPie. A typo fix becomes a
  one-line prose diff.

### 3.3 Render at build time; ship real HTML

The generator renders full pages (title, nav with current-page marker,
dialog, keyword panel, prev/next) into static HTML. Client JS shrinks to two
small, optional enhancements: the theme toggle and the hover-tooltip
positioning. This fixes SEO, no-JS, first paint, and per-chapter
`<title>`/`<meta description>`/OG tags in one move.

Whether to implement this as ~300 lines of bespoke Node (the repo's current
ethos — it already owns three generators) or to adopt **Eleventy or Astro**
(templates, Markdown, dev server, asset hashing for free) is a taste call.
Recommendation: bespoke is fine *if* §3.2's Markdown pipeline is adopted;
choose Astro only if appetite exists for a larger one-time migration. What is
not fine is the status quo: three bespoke generators that emit empty shells.

### 3.4 One stylesheet, one token set

- A single `assets/site.css` shared by every page, with **one** design-token
  vocabulary (`--bg`, `--surface`, `--text`, `--muted`, `--accent`,
  `--code-*`) defined once per theme:

  ```css
  :root { /* light (solaris) tokens */ }
  [data-theme="dark"] { /* dark tokens */ }
  @media (prefers-color-scheme: dark) { :root:not([data-theme]) { ... } }
  ```

- Theme = one `data-theme` attribute on `<html>`, one ~10-line inline script
  in `<head>` (reads `localStorage`, prevents FOUC), default follows the OS.
  Delete the query-parameter propagation, the three sync implementations,
  and the per-link URL rewriting.
- Page-specific CSS (playground layout, chat bubbles) lives in small
  per-section files layered on the shared tokens — never re-declaring them.

### 3.5 Clean repository, CI build, automatic deploy

- Remove from git: all compiled `.js`, generated `.html`, `playground/dist/`,
  and `node_modules/**`. `npm ci` installs the toolchain like every other
  project.
- GitHub Actions workflow: `npm ci && make build` (plus a link checker and
  `tsc --noEmit`), deploy the output directory via `actions/deploy-pages`.
  PRs get build + link-check gating; `main` deploys itself.
- Cache busting via content hashes from the bundler (`main.[hash].js`),
  deleting the hand-maintained `?v=2026…` strings.
- Move `draft/`, `technical-template.html`, and `benchmarks` out of the
  deploy root (into `docs/` or a non-published folder); delete
  `language-reference.html` and the `installation.html` stub (or make the
  stub a server-side 301 via the Pages redirect pattern).

### 3.6 One build toolchain

esbuild for everything (it is already a dependency): ESM modules with real
imports, shared types in one `src/types.ts`, a `tsconfig.json` for
`tsc --noEmit` type checking, `esbuild --watch` + any static file server for
dev, Prettier for both TS and Markdown content. The Makefile shrinks to
`build` / `dev` / `check` targets that call these.

## 4. Target design — aesthetics

### 4.1 One visual identity

Today the homepage defaults light, docs templates default dark with a light
override class, accents differ, and the "technical template" is a third
snapshot. Pick the Solarized-paper identity (it suits the book-like dialog
format and is already the shipped default) as the canonical light theme,
derive the dark theme from the same token sheet, and let every page inherit
them. The user-visible win: navigating from homepage → tutorial → manual no
longer feels like visiting three different sites.

### 4.2 A real landing page

The homepage should answer "what is PyPie and why should I care" in five
seconds, *then* offer the playground:

1. **Hero**: one sentence ("Tensor programming with shapes checked before you
   run") + one small, beautiful, typed code sample with hover-types live —
   the site's signature trick, above the fold.
2. **Three claims with evidence**: compile-time shape checking, automatic
   parallelization, concise high-level code — each with a 4-line snippet,
   sourced from the same build-time-checked pipeline as chapters.
3. **Embedded playground below** (or one click away), lazy-loaded: don't pay
   the 1.3 MB editor bundle + Pyodide boot until the user scrolls to it or
   clicks "Run". Keep exactly one playground page; delete the drifted twin.
4. Clear primary action: "Start the tutorial".

The current About-drawer text is good copy — promote it to the hero instead
of hiding it under the editor.

### 4.3 Typography and rhythm

Space Grotesk + IBM Plex Mono is a good, distinctive pairing — keep it, but:

- Self-host the two families as `woff2` with `font-display: swap` and
  preload, replacing 23 copies of a render-blocking CSS `@import` chain.
- Establish a type scale and spacing scale in the token sheet (the current
  per-page `clamp()` values are all slightly different by accident).
- Cap measure at ~70ch for dialog text (already roughly done) and align the
  keyword panel's baseline grid with the chat thread.

### 4.4 Dialog presentation refinements

The teacher/student dialog is the site's soul (in the Little-Typer lineage) —
keep the format, polish the rendering:

- Drop the forced `min-height: 6.4rem` on bubbles; short replies ("Yes!")
  should be short. The uniform tall bubbles currently waste vertical rhythm
  and make scanning harder.
- Name the speakers once per chapter (full names or roles on first bubble,
  initials after), so "D"/"W" isn't a riddle for newcomers.
- Bubble index numbers are useful for citation — make them anchor links
  (`#msg-12`) so readers can share a specific exchange.
- Code blocks inside bubbles render the same as standalone blocks (today they
  share most styling but have separate radius/margin rules in only one of the
  three templates).

### 4.5 Navigation and wayfinding

- Top bar marks the current section (`aria-current` exists in the side nav
  but the top bar never indicates where you are).
- Chapter pages get prev/next footers driven by the manifest, so readers can
  flow through the tutorial without the sidebar.
- "Updates" gets an index page (reverse-chronological list with leads) and an
  Atom feed; the nav links to the index, not to a hardcoded latest post.
- Add favicon, per-page meta descriptions, OG/Twitter cards, sitemap.xml,
  robots.txt — all generated by the build from the manifest.

### 4.6 Performance is an aesthetic

- Static HTML + tokens-in-head = no theme flash, no content pop-in.
- Lazy playground bundle (see 4.2); Pyodide boot starts on intent (focus or
  Run hover), with the existing status line showing progress.
- Hashed assets + long-lived cache headers replace the hand-bumped `?v=`.

### 4.7 Accessibility

Focus styles and aria labeling are already better than average — preserve
them through the migration, and fix the gaps: verify muted-text rgba values
meet WCAG AA against both themes (several ~0.68–0.72 alpha grays are
borderline), give the hover tooltip a keyboard path (focusable tokens that
show the same `data-type` content), and ensure bubbles read sensibly in
screen-reader order (speaker, then text — currently true; keep it tested).

## 5. Proposed repository layout

```
site.config.ts              # sections, chapters, nav — single manifest
content/
  learn/00-overview.md      # front matter + dialog markdown + pypie fences
  learn/08-transformer.md
  manual/...
  updates/2026-05-25-....md
src/
  build/render.ts           # markdown → HTML (uses templates/)
  build/pypie-analyze.ts    # runs real PyPie toolchain over fences
  templates/chapter.html    # ONE template
  runtime/theme.ts          # tiny client enhancements
  runtime/hover.ts
  playground/               # editor app (lazy-loaded ESM)
assets/
  site.css                  # tokens + shared styles
  fonts/
public/                     # favicon, robots.txt, static passthrough
dist/                       # build output — gitignored, deployed by CI
.github/workflows/site.yml  # build, typecheck, linkcheck, deploy
```

## 6. Migration plan (each phase ships independently)

| Phase | Work | Risk | Pays for itself by |
|---|---|---|---|
| 0 | CI build + Pages deploy; stop committing `*.js`, generated `*.html`, `dist/`, `node_modules`; add `tsconfig.json` | Low | Ending double-diffs and artifact drift immediately |
| 1 | Extract `site.css` + single token set + `data-theme` theming; delete `?theme=` propagation and two of three theme implementations; self-host fonts | Low | Every page restyles from one file |
| 2 | Merge the three engines: one template, one generator, one shared runtime, manifest-driven nav; delete `updates/manual-shared.ts` etc.; remove orphan pages | Medium | Section count can grow without copying an engine |
| 3 | Markdown content pipeline + build-time PyPie analysis of `pypie` fences; port chapters one at a time (start with `learn/types`, 139 lines; end with `transformer`); static HTML output, per-page meta | High effort, mechanical | ~26k lines of content-as-code become prose; snippets are compiler-verified |
| 4 | Landing page redesign, lazy playground, updates index + feed, sitemap/OG/favicon, dialog polish | Low | Public face matches the quality of the language |

Phases 0–2 are pure consolidation with no visible change. Phase 3 is the big
one but can be ported chapter-by-chapter behind the same URLs. Phase 4 is
where the aesthetic improvements land visibly.

## 7. What to keep

- **The dialog teaching format** — it is the brand; fix its rendering, not
  its concept.
- **Typed-hover code blocks** — no other language site has this; make the
  data come from the compiler instead of by hand.
- **The Solarized-paper identity and font pairing** — distinctive and
  book-like; unify rather than replace.
- **The playground's worker/LSP architecture** (`pyodide-worker.ts`, the
  one-source-of-truth invariant in `docs/playground_hover.md`) — this
  proposal extends that same invariant to the documentation.
- **Zero-framework runtime** — the *shipped* site needs almost no JS; keep it
  that way. The build can be smarter so the client can stay simple.
